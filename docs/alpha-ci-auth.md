# Main-only CI access to Alpha

The user approved this scoped integration and the reviewer-only cutover after auth, billing, artifact, rollback, and connectivity checks pass. The implementation is prepared; no CI certificate authority, signing role, federated network client, or Alpha deployment account has been provisioned. Existing read-only OpenBao machine identities cannot establish this trust. Use the existing PC operator sessions, never copy their credentials to CI or this thread.

The protected deployment job uses GitHub OIDC twice: a two-minute OpenBao token signs a ten-minute, ephemeral Ed25519 SSH identity, and Tailscale workload federation admits a temporary network node. The signing token is revoked immediately. The workflow removes the private key afterwards; it never uploads it. PR jobs have no `id-token: write`, network identity, runtime secrets, or production SSH access.

## Operator setup

1. In an existing authenticated OpenBao administrator session, establish **`auth/github-actions`** using the GitHub issuer `https://token.actions.githubusercontent.com` and its discovery document. Preserve any existing roles and refuse a conflicting issuer. Apply [the exact JWT role](alpha-ci-openbao-role.json) as `auth/github-actions/role/ts-reviewer-alpha` and [the policy](alpha-ci-ssh-policy.hcl) as `ts-reviewer-alpha-ssh`. The role binds the immutable repository and owner IDs, protected `alpha` subject, `main`, push events, and this workflow. It grants only one SSH-signing endpoint and self-revocation: no KV reads, secret writes, other signers, or administrative access. The vendor's `token_no_default_policy` field is required to prevent incidental access from its default policy.
2. Use an existing compatible **`ssh-client-signer`** OpenBao SSH backend, or create it under the approved scoped integration. Generate a new CA inside OpenBao only if none exists; never replace an existing CA or export its private key. Apply [the signing role](alpha-ci-ssh-role.json) as `ssh-client-signer/roles/ts-reviewer-alpha`. Its vendor-required certificate permission fields allow only the dedicated user, ten minutes, no host certificates or forwarding extensions. Deliver only its public CA to Alpha through the HomeLab control plane.
3. Declare the dedicated **`ts-reviewer-deploy`** Alpha account and SSH CA trust through HomeLab's host configuration. Keep it distinct from uid/gid 1654, operator accounts, root, and the Incus/Harbor groups. Deployment authority can choose code that runs with reviewer credentials; the fixed launcher limits its host-root operations. Protect main and trust every deployed artifact accordingly. Disable password login, TTYs, agent/X11/TCP forwarding, and tunnels for it. Limit certificate principals to this account. Install the reviewed self-contained `deploy/deploy-alpha` artifact root-owned `0755` at **`/usr/local/libexec/ts-reviewer-deploy`**, with `NOPASSWD` permission for that exact executable only. The utility validates the fixed reviewer target, commit/digest, handoff, files, and mounts; application preflight drops to uid/gid 1654 with no new privileges. Never grant `sudo` on uploaded executables or a shell. Future utility updates remain an operator-reviewed control-plane operation.
4. On your PC, open [Tailscale Trust credentials](https://login.tailscale.com/admin/settings/keys), create a federated client for the GitHub issuer with audience **`https://github.com/TerraScale/ts-reviewer/alpha`**, and bind the same repository/owner, `alpha` subject, `main` ref, push event, and workflow claims. Permit only `auth_keys` issuance for **`tag:ts-reviewer-deploy`**. Add a network grant from that tag to Alpha's verified Tailscale IP, **`100.109.206.68`**, TCP 22 only. Existing grants are additive: verify no wildcard grant gives this tagged node wider access. Keep Tailscale SSH off; OpenSSH performs certificate authentication. Place its vendor-issued public client ID in the GitHub **`alpha` environment variable `TAILSCALE_ALPHA_CLIENT_ID`**, and the independently verified Alpha Ed25519 public host key in **`ALPHA_HOST_ED25519_PUBLIC_KEY`**. These unavoidable third-party public identities are not tuning settings or secrets. Keep their authoritative copies in OpenBao's existing control-plane inventory; no OAuth secret or operator key is required in GitHub.
5. Before the first merge, validate that an equivalent untrusted branch/PR token is rejected by both providers, a trusted main deployment identity reaches only Alpha TCP 22, and SSH cannot authenticate as another user or invoke arbitrary root commands. Inspect the complete HomeLab plan and apply only the approved reviewer changes. Validate billing identity and current-day cost coverage, PEM/dotenv delivery, root-only rollback snapshot, installed root launcher, and exact checked image. Keep `/var/srv/appdata/ts-reviewer` root-owned, traversable by uid 1654, and unwritable by the runtime or deployment accounts; rollback copies rely on that boundary. Confirm `setpriv` exists, `/tmp` permits execution, and dropped-uid offline configuration preflight can access its working directory and HOME. No deployment or automatic recovery starts until these conditions pass.

An existing authenticated operator can apply the source-only OpenBao policy/role files without passing credential values:

```sh
bao policy write ts-reviewer-alpha-ssh docs/alpha-ci-ssh-policy.hcl >/dev/null
bao write auth/github-actions/role/ts-reviewer-alpha @docs/alpha-ci-openbao-role.json >/dev/null
bao write ssh-client-signer/roles/ts-reviewer-alpha @docs/alpha-ci-ssh-role.json >/dev/null
```

These commands presume the reviewed issuer/backend already exists, TLS verification is enforced, and `BAO_ADDR` is the documented OpenBao origin. They change security policy and require the approved operator session; machine read access cannot run them. Keep credential values out of terminal arguments, printed environment variables, debug logging, GitHub variables, and PR artifacts.
