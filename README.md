# ts-reviewer

`ts-reviewer` is TerraScale's evidence-backed Forgejo pull-request reviewer. It runs only for pull requests targeting `main`, reviews each new head, posts inline findings and a summary, requests changes and fails the required `ts-reviewer` status for any finding regardless of severity, and approves the pull request with a successful status only when there are no findings (so branch protection requiring an approval can merge on a clean review).

Reviews run through [OpenCodeReview](https://github.com/alibaba/open-code-review) (`ocr`, bundled in the image): each review fetches the pull request with the Forgejo token as a blobless partial clone (full history for the merge-base, but no file contents until needed, so a repository with hundreds of MiB of history fetches in about a second), checks out the exact head, downloads the other side of every changed file by running the same merge-base diff ocr runs, and runs `ocr review --from <base> --to <head>` with lazy fetching disabled (ocr's git has no credentials, and everything it reads is already local) with ocr's `OCR_LLM_*` endpoint variables pointed at ts-router's Anthropic-compatible endpoint (which passes requests to CLIProxy) and a generous per-request `OCR_LLM_TIMEOUT` because large file groups take a while (ocr retries each request 5 times on top of that; raising the per-request attempt count further belongs to the proxy's `request-retry`, not ocr, which hardcodes its SDK retry limit). When some file groups still fail, the reviewer resumes ocr's session (`ocr review --resume <session>`): completed items and their findings are reused and only the failed items are reviewed again, with exponential backoff between attempts. Reviews run on GPT-6.1 Sol at medium reasoning effort only, which serves many concurrent streams, so there is no fallback model by default. When one is configured (`TS_REVIEWER_FALLBACK_MODEL`) and the review model still cannot finish after `TS_REVIEWER_OCR_MAX_ATTEMPTS` runs, the fallback model resumes the same session with its own attempts, so it only reviews the file groups the first model failed and the summary notes that it took over; a review already running on the fallback model does not fall back. The model is passed as ocr's explicit `--model` flag, which is what lets a resumed session switch models. A review without findings passes only when every selected item was reviewed; findings from a partial review still request changes. Error statuses quote the failing command's own error line (ocr's `Error:` or git's `fatal:`), never ocr's JSON usage report. ocr's line-level findings (path, line, severity, suggestion) are mapped to review comments, deduplicated, and posted through the Forgejo API. The image ships git (>= 2.41) and the static `ocr` binary; no Node.js is involved. Comment `@terrascale-bot escalate` on a pull request to re-review the same head with the stronger escalation model (`TS_REVIEWER_ESCALATION_MODEL`, default `gpt-6-astra` on the same endpoint). With a fallback model configured, reviews share a budget of `TS_REVIEWER_PRIMARY_STREAMS` concurrent ocr requests on the review model: each review takes up to `TS_REVIEWER_OCR_CONCURRENCY` of the free streams and runs ocr with that many, and once none is free a new review starts on the fallback model right away (its summary says so) instead of failing on a rate-limited review model first.

## Runtime

Required environment variables are `TS_REVIEWER_FORGEJO_TOKEN`, `TS_REVIEWER_PROXY_TOKEN`, `TS_REVIEWER_WEBHOOK_SECRET`, `TS_REVIEWER_CONTEXT_API_TOKEN`, and the separate `TS_REVIEWER_OPERATOR_TOKEN` (the proxy only serves the review model). Optional variables include `TS_REVIEWER_LISTEN` (default `http://+:8080`), `TS_REVIEWER_FORGEJO_URL`, `TS_REVIEWER_PROXY_URL` (default `http://10.11.99.1:8318`, ts-router), `TS_REVIEWER_MODEL` (default `gpt-6.1-sol(medium)`, GPT-6.1 Sol at medium reasoning effort through CLIProxy's effort suffix), `TS_REVIEWER_ESCALATION_MODEL` (default `gpt-6-astra`), `TS_REVIEWER_FALLBACK_MODEL` (default empty, no fallback), `TS_REVIEWER_MAX_CONCURRENT` (default `32`, review workers), `TS_REVIEWER_OCR_CONCURRENCY` (default `16`, bounded to 1–64 OCR subtasks per review), `TS_REVIEWER_PRIMARY_STREAMS` (default `64`, concurrent review-model requests across all reviews before new reviews spill to the fallback model; only used with a fallback model), `TS_REVIEWER_OCR_MAX_ATTEMPTS` (default `3`, bounded to 1–20 ocr runs per model, each resuming the previous one, before the review falls back or is reported incomplete), `TS_REVIEWER_OCR_RETRY_BASE_DELAY` (default `00:00:10`, doubled per retry, capped at ten minutes), `TS_REVIEWER_OCR_LLM_TIMEOUT` (default `00:20:00`, per LLM request, bounded to one minute–two hours), `TS_REVIEWER_OCR_ITEM_TIMEOUT` (default `01:00:00`, per ocr file group, bounded to one minute–24 hours), `TS_REVIEWER_TIMEOUT` (default `04:00:00`, per running review including every retry), `TS_REVIEWER_CONTEXT_MAX_ATTEMPTS` (default `5`), and `TS_REVIEWER_CONTEXT_RETRY_BASE_DELAY` (default `00:00:01`, capped at one minute). Accepted reviews publish a pending `ts-reviewer` status (`Review queued`, then `Review in progress`). Each pull request has at most one queued and one running review: a newer request replaces the queued one, a push cancels the running review of the old head (even when another request is already queued), a request for the head already under review is dropped, and closing the pull request cancels its work. A head whose review is dropped this way gets a `skipped` `ts-reviewer` status (`Review skipped: a newer push replaced this head` or `…: the pull request was closed`) instead of keeping a pending one forever; a running review is marked only once it has stopped, and a shutdown marks nothing so startup recovery still finds the pending head. Queued work waits for a worker without expiring; `TS_REVIEWER_TIMEOUT` bounds each running review. On startup the reviewer queues every open pull request whose head still shows a pending `ts-reviewer` status or has none at all, so a restart neither strands accepted reviews nor misses pushes delivered while it was down. Comments written by the bot never trigger a review. Configure a Forgejo webhook for push, pull-request, and issue-comment events at `/webhook`.

Every push to a branch queues exact-commit indexing in a bounded, deduplicated queue backed by the embedded LiteDB context database (`TS_REVIEWER_CONTEXT_DATABASE`, default `data/reviewer-context.db`). The database opens in shared mode for rolling deployments and multiple reviewer processes. Pending jobs are replayed after a process restart and removed only after a successful atomic commit replacement. Failed jobs persist their attempt count, next retry time, and last error; exponential retry is bounded and jobs move to a durable dead-letter state after the configured attempt limit. Search uses LiteDB's built-in vector index (HNSW, cosine), and text embeddings are produced locally by a bundled ONNX model run on an explicit single-threaded onnxruntime session per inference, spread across up to eight inputs at a time (onnxruntime's default pins a thread per host core, which fails inside a CPU-limited container) (`SmartComponents.LocalEmbeddings`, 384 dimensions) that is downloaded once at build time — no external embedding service is needed at runtime. Startup rejects missing or blank authentication secrets. Every webhook requires a valid SHA-256 HMAC in `X-Forgejo-Signature`; every `/context/search` request requires `Authorization: Bearer <context token>`, including on private networks. Supply secrets through the deployment secret store and use distinct, randomly generated values. There is no unauthenticated development mode. When the reviewer picks up a pull request or a `@terrascale-bot` command it reacts with 👀 so authors can see it is working.

Never put tokens in the image, workflow YAML, or command-line arguments. The Forgejo token needs pull-request read, review/comment/status write, and issue write access across the TerraScale organization. The proxy token should be reachable only from the homelab network.

## Container release

The service targets .NET 11 and is built from `src/TerraScale.Reviewer/TerraScale.Reviewer.csproj`. Feature slices live below that project directory, while tests are in `tests/TerraScale.Reviewer.Tests/`. Run local checks with `dotnet build src/TerraScale.Reviewer/TerraScale.Reviewer.csproj` and `dotnet run --project tests/TerraScale.Reviewer.Tests/TerraScale.Reviewer.Tests.csproj` (TUnit). The release image is built from `Containerfile` on Debian trixie-slim, which adds git and the sha256-pinned static `ocr` binary: first publish a self-contained single-file binary with `dotnet publish src/TerraScale.Reviewer/TerraScale.Reviewer.csproj --configuration Release --runtime linux-x64 --self-contained true --output artifacts/ci/container-publish -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:DebugType=None`, then run `podman build --platform linux/amd64 --file Containerfile .`.

The context API accepts `POST /context/search` with `{ "repository": "TerraScale/ts-reviewer", "commit": "<sha>", "query": "Forgejo webhook authentication", "top_k": 8 }` and returns source snippets with repository, path, line range, symbol, and cosine-score metadata. Search applies the repository/commit boundary before a bounded exact cosine ranking, preserving tenant/commit isolation while avoiding vector-index writes during request-time reads. Reviews run through ocr and do not read this index; the context API serves other clients. Operators can inspect bounded dead-letter metadata with `GET /admin/context/dead-letter` and replay one job with `POST /admin/context/dead-letter/replay` using the separate operator bearer token; responses never expose lease tokens or indexed source content.
CI (`.forgejo/workflows/ci.yml`) tags the image by immutable commit SHA. Pull
requests only build and inspect it; pushes to `main` push the image tested in
the same job to `git.terrascale.tech/terrascale/ts-reviewer:<sha>` with the
`TERRASCALE_BOT_TOKEN` organization secret. The homelab deployment supplies the
public webhook URL and secrets.

Deploying the LiteDB-based image over a pre-LiteDB deployment: mount a
persistent volume at the context database directory (the parent of
`TS_REVIEWER_CONTEXT_DATABASE`, default `data/`) or every restart re-indexes
from scratch, and delete any previous SQLite `reviewer-context.db` file in that
directory first — LiteDB refuses the old file format and the service exits at
startup.
